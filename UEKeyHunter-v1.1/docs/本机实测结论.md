# 本机实测结论（Yuna 0.4.70731a / UE4.27）

记录人：夜煞　时间：2026-11-03

## 一、目标

从 `E:\alkins\Yuna 0.4.70731a\Yuna\Binaries\Win64` 找出这把游戏的 AES key，
并解释 `AES_finder.exe` 为什么跑 25 秒就吐 `Key not found. Game archives are probably not encrypted.`

## 二、容器事实

### pak 尾部 FPakInfo（@40235882）

```
magic            E1 12 6F 5A
version          11 (0x0b)
indexOffset      39972441
indexSize        57472
indexHash        a8564705e315d27f196069e69fcb5b272178e787 (SHA-1)
```

（indexOffset=1486288, indexSize=3939852）。全文件只有 1 处真 magic。

## 三、加密证据（不是"大概"）

- pak 每 MB 可打印率 31.9%~38.3%、零字节率 0.4%~17.4%，无成片明文。
- 全 pak 搜 `../../../`、`Content/`、`.uasset`、`.uexp` → **0 命中**。
- utoc（4.6MB）内除 1 处明文 `Oodle`（@1267550）外，**搜不到任何路径字符串**。

## 四、AES_finder 为什么失败

它的做法是：在 exe 里找 32 字节候选 → 拿候选去解 pak 索引 → 检查解出来像不像挂载点。
找不到就打印兜底文案 `archives are probably not encrypted`（**这是兜底文案，不是结论**）。

实测：**这把 key 不以连续 32 字节形式存在于 exe 里**。

| 扫描对象 | 大小 | 偏移覆盖 | 校验器 | 命中 |
|---|---|---|---|---|
| `Yuna-Win64-Shipping.exe` | 88,080,896 | **全量，stride=1** | 6 个 | **0** |
| `Yuna.exe`（启动器） | 266,752 | 全量 | 6 个 | **0** |

扫描器：`lib/aes256.js`（1,075,269 keys/s，500 组随机向量对比 node:crypto 误差 0）

六个校验器：

1. pak 索引 @39972441 → 挂载点 FString
2. pak 索引 @1486288 → 挂载点 FString
3. pak @0 → 资产标签 `C1 83 2A 9E`
4. pak @40234858 → 资产标签
5. ucas @0 → 资产标签
6. ucas @1048576 → 资产标签

耗时 379 秒，**hits = 0**。

## 五、其他被排除的路线

- `F:\模型\PakMaster\configs\repak-aeskey.json` 里那把 `0x01DA1F49…EA D5C2DD`：
  用它解索引 → `SHA1 = 57b82844c52301776806c6fa3dd30d25cd26d3e9`，与存储值 `a8564705…` 不符，明文头全乱码。**不是这个游戏的。**
- 全 exe 里 64 字符 hex 明文候选只有 32 处，全部不匹配。
- exe 里 `Content/`、`.uasset`、pak 文件名 `Yuna-WindowsNoEditor` 字符串 **0 命中**。
  `"PakFile"` 命中 5 处（66008916 / 70652000 / 70652776 / 70652872 / 70652904），`"AES"` 命中 5 处（5462080 …），周边都不是 key。
- 游戏目录全盘没有 crypto/ini/json 之类的 key 配置。

## 六、下一步（唯一有戏的）

1. 启动游戏，进到主菜单（让 pak/ucas 完成挂载）；
2. `dump-mem.ps1 -ProcessName Yuna-Win64-Shipping`（建议 `-MinRegionMB 4 -MaxTotalMB 4096`）；
3. `scan-mem.js`，用同一套校验器扫内存；
4. 命中后用 `verify-key.js` 做整索引 SHA-1 复核 —— 一致即为真 key。

速度参考：6 校验器 227k keys/s，2GB 内存约 2.4 小时；单校验器 1.07M keys/s，2GB 约 30 分钟。
可以先只抓 ≥16MB 的大区域，命中率高且总量小。

## 七、旁注

- 40MB 的 `.pak` 相对 6.4GB 的 `.ucas` 基本是个壳，游戏数据都在 IoStore 里。
- `retoc 0.1.5` 读不了这个容器（`Error: failed to fill whole buffer`，info/list/verify 都报同一个错，
  失败发生在加载容器阶段）。换 FModel 那类工具更可能直接吃进去。

## 2026-11-03 结论更新：key 找到了

**key = 0xf6f3af0fd8bfacce777fc2ef4a5377d969d0d9e80504566e7889c815c7d9ca4c**

- 校验：用它 AES-256-ECB 解 `Yuna-WindowsNoEditor.pak` 索引（offset 39972441, size 57472），
  解得 SHA1 = `a8564705e315d27f196069e69fcb5b272178e787`，与 pak 尾部 FPakInfo 存的 indexHash 完全一致。
- 明文开头 = `0A 00 00 00 "../.." ... 00`（FString 挂载点 "../../../"），条目数 3943。
- 发现位置：**运行时内存**（游戏跑起来后 dump 5,000 MB / 16,948 个区域，stride=8 一扫即中），
  文件是 `mem\Yuna-Win64-Shipping\r_1bfd3c30000_10000.bin`。
- **exe 里没有**这把 key（88,080,896 字节，全偏移 stride=1、6 个校验器，0 命中）——所以 AES_finder 扫 exe 永远扫不到，
  它吐的 "Game archives are probably not encrypted" 只是找不到 key 时的兜底文案。
- 期间踩的最大坑：`isMountPoint` 里用 `len` 而不是 `len-1` 判可打印字符，把 FString 结尾的 `\0` 当非法字符否掉，
  导致对正确 key 恒返回 false，白扫 2.2 亿次 exe + 5GB 内存。已修，并加了 `_selftest_oracle.js` 自检。
